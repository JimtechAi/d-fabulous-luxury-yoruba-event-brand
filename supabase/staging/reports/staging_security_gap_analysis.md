# Staging security gap analysis (production `public` schema, as exported)

Source: `supabase/staging/source/production_public_schema.sql`, SHA-256 `f41bf2fee49c315b0b6806552f512960381c635907cc88a73004b1f708f2ad50`, 52,351 bytes, dumped from PostgreSQL **17.6** by pg_dump 17.11.
Method: static reading of the file plus `scripts/generate-production-inventory.mjs`. **No SQL was executed against any database.** Line numbers refer to the export.
Evidence grades: **CONFIRMED** (stated by the export), **CONFIRMED + CODE** (export plus application source), **INFERRED** (follows from documented PostgreSQL/Supabase behaviour but needs a read-only check on staging), **UNKNOWN** (outside a public-only dump).

## 2. Gaps in the existing remediation package (A, B, C) against the real schema

| ID | Gap | Detail | Action required (not performed) |
|---|---|---|---|
| G1 | **No privilege normalisation exists** | Nothing in the package removes the default-privilege grants that a restore leaves on staging (S7). | Write and test a privilege-normalisation proposal generated from the inventory (revoke API-role grants on all 12 tables, 12 functions, the sequence; re-grant exactly the 35 dumped grants). Run read-only compare afterwards. |
| G2 | **A's policy name does not exist in production** | A step 1a looks up `user_permissions_manage_owner_admin`; production's policy is `user_permissions_manage_active_owner_admin`. The lookup returns nothing, so the `FOR ALL` policy is neither dropped nor replaced by a SELECT-only one. Outcome is still safe only because the **restrictive** deny policies and REVOKEs run regardless. A's `audit_logs_insert_owner_admin` and `Users update own profile` drops are no-ops (those policies are absent); production's `Users update profile` and `Admins can update profiles` remain but are neutralised by the restrictive policies. | Adapt A to the real names, or make it name-agnostic; extend A's verification script (`20261112_99_verify_readonly.sql`). |
| G3 | **A never revokes `MAINTAIN`** (PostgreSQL 17) and covers only `profiles`, `permissions`, `user_permissions`, `audit_logs`. After A, `authenticated` still has `MAINTAIN` there (lock-table denial of service, VACUUM/REINDEX) and keeps `TRUNCATE`/`TRIGGER`/`REFERENCES` on all other tables. | Extend the revoke list (`MAINTAIN` everywhere; `TRUNCATE`, `TRIGGER`, `REFERENCES` on all tables for `anon` and `authenticated`). |
| G4 | **B changes the function to SECURITY INVOKER** | Correct for `current_user = 'service_role'`, but depends on PostgREST switching the DB role to `service_role` and on `authenticated` keeping EXECUTE on `is_owner()` (it has it: dump 1515). Not testable offline. After B, **any** holder of the service key can promote any account to `owner`; only the API's own hierarchy (`lib/userPolicy.ts`) restrains it. | Staging functional test with real keys; record as an accepted trust boundary. |
| G5 | **Ledger immutability is not a proposal item** | S6 is production reality, not a repository assumption; the previous plan's step 07 targeted a state production never had. | Decide: reproduce production as-is on staging, or add a reviewed payments-immutability proposal. |
| G6 | **`service_role` lacks DELETE on `profiles`** | S8; also `bookings`/`payments`/`messages` have no service DELETE (the code deletes bookings with the caller's token, which is fine). | Decide whether to grant `DELETE` on `profiles` to `service_role` (proposal) or change the API to delete the Auth user and rely on `ON DELETE CASCADE` (`profiles_id_fkey`). |
| G7 | **C's "payment ledger" side effect is moot** | C's header warns it tightens the payments guard; production has no such trigger, so C only changes the two helpers. Its preflight (`is_active` exists, B applied) will pass on this schema. | Update the proposal text. |
| G8 | **`security_remediation_snapshots`** | A, B and C all create `public.security_remediation_snapshots` (RLS on, privileges revoked from API roles). Under S7 the new table would also receive default grants if the REVOKE were missing; the proposals revoke explicitly, which is correct. | Keep; include the table in the staging cleanup list. |

## 4. Verdict

The export is a trustworthy, credential-free baseline, but it describes a **hardened-in-places, inconsistent** production database. Staging must not be built from the repository's install steps, and must not be built from a verbatim restore either, until privilege normalisation (G1) exists and the unknowns in `staging_installation_recommendation.md` are inspected.
